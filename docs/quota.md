# 쿼터

AIPool이 각 계정의 쿼터를 파악하는 방식, 선택적으로 켤 수 있는 두 가지 백그라운드 작업, 그리고 모든 쿼터가 소진되었을 때 일어나는 일을 설명합니다.

## 쿼터를 파악하는 방식

AIPool은 기본적으로 **수동(passive)** 방식으로 동작합니다. 즉, 프록시를 거쳐 가는 응답에서 `anthropic-ratelimit-unified-*` 헤더를 읽습니다. 아직 요청을 처리한 적이 없는 계정은 로테이션이 처음 그 계정에 도달할 때까지 쿼터가 unknown으로 표시됩니다.

관측된 쿼터는 설정 파일 옆의 `aipool.state.json`에 저장되므로, 재시작해도 로테이션 상태가 유지됩니다. 오래된 창은 자동으로 폐기되며, 이 파일은 삭제해도 안전합니다. 쿼터는 트래픽을 통해 다시 파악됩니다.

## 계정 풀 쿼터 엔드포인트

`GET /aipool/quota`는 Claude Code 상태 표시줄처럼 가볍게 쓰는 소비자를 위한 쿼터 데이터를 반환합니다. 여기에는 모든 계정의 관측된 한도와 함께, 공유 5시간 창, 공유 주간 창, Sonnet 주간 창, Fable 주간 창에 대해 티어 가중치를 적용한 계정 풀 집계값이 들어 있습니다. Anthropic이 전용 버킷을 보고하지 않는 계정에서는 Sonnet과 Fable이 공유 주간 버킷을 대신 사용합니다. 최상위 `warmup` 객체는 keep-warm이 꺼져 있는지, 일정 간격으로 동작하는지, 매일의 리셋 목표 시각에 맞춰 예약되어 있는지, 아니면 기준점(anchor)에 맞춘 5시간 주기로 동작하는지를 알려 줍니다. 예약 모드에는 설정된 시간대, 놓친 실행에 대한 정책, 다음 워밍업/리셋 타임스탬프가 포함되며, rolling 모드에는 `anchorResetAt`, `cadenceSeconds`, `nearResetToleranceSeconds`, `postResetBufferSeconds`도 포함됩니다.

구독 용량은 Claude Pro를 기준으로 가중치를 매깁니다. Pro와 Team Standard는 `1`, Max 5x와 Team tier 1은 `5`, Max 20x와 Team tier 2는 `20`입니다. AIPool은 OAuth 프로필에서 조직과 좌석(seat) 티어를 읽습니다. 인식할 수 없는 티어는 `accounts`와 `unknownTiers` 아래에 계속 표시되지만, 추측한 가중치를 부여하는 대신 집계에서 제외됩니다. API 키의 토큰 및 요청 한도는 그 단위를 구독 사용률과 합산할 수 없으므로 계정별로 따로 유지됩니다.

원격 호출자는 다른 제어 엔드포인트와 똑같은 방식으로 인증합니다:

```bash
curl -H "x-api-key: $AIPOOL_API_KEY" https://proxy.example.com/aipool/quota
```

선택 기능인 쿼터 프로브는 처음으로 갱신에 성공할 때 누락된 티어 메타데이터도 채웁니다. 티어 메타데이터는 관측된 쿼터와 함께 `aipool.state.json`에 저장되므로 이후 재시작해도 유지됩니다.

## 쿼터 프로브

유휴 계정의 쿼터도 최신 상태로 유지하고 싶다면 백그라운드 프로브를 켭니다:

```bash
aipool probe 300    # 300초마다 갱신
aipool probe off    # 수동 방식으로 복귀(기본값)
aipool probe        # 현재 설정 표시
```

TUI 설정 화면(`g`)의 **Quota probe** 행도 같은 역할을 하며, 메인 화면에서 `p`를 누르면 모든 계정을 한 번 갱신합니다.

프로브는 각 OAuth 계정의 사용률을 해당 제공자의 읽기 전용 사용량 엔드포인트에서 읽어 옵니다. 이 엔드포인트는 **메시지 쿼터를 전혀 소모하지 않고** 쿼터를 보고합니다. Anthropic 계정은 `/api/oauth/usage`를 사용하고, Codex 계정은 ChatGPT의 내부 엔드포인트인 `/backend-api/wham/usage`를 사용하며 각 계정의 `ChatGPT-Account-Id`가 필요합니다. API 키 계정과 서드파티 계정은 건너뜁니다. Codex 엔드포인트는 공개 OpenAI API에 속하지 않으므로 예고 없이 바뀔 수 있습니다. 최소 간격은 30초입니다. 간격을 바꾸면 실행 중인 서버에 즉시 반영됩니다.

요금제가 **Sonnet 7-day** 버킷을 제공하는 경우, 이 버킷의 유일한 출처도 프로브입니다. Fable 주간 버킷은 응답 헤더(`anthropic-ratelimit-unified-7d_oi-*`)를 통해 수동적으로 들어오므로, 프로브를 켜지 않아도 Fable을 고려한 라우팅이 동작합니다. 두 모델 계열 모두 페이로드의 `limits[]`에서 읽으며, 업스트림은 이 항목에 해당 계정에 실제로 적용되는 모델별 주간 상한을 나열합니다.

### 소진된 모델 계열 버킷 재검증

이 `7d_oi` 헤더는 **Fable 응답에만** 실려 오며, 다른 모델의 응답에는 포함되지 않습니다. 그래서 소진된 Fable(또는 Sonnet) 측정값은 스스로 고착됩니다. 측정값이 전환 임계값 이상이 되면 로테이션은 그 계정으로 해당 계열의 요청을 더 이상 보내지 않는데, 측정값을 갱신할 수 있는 유일한 수단도 바로 그 요청이기 때문입니다.

따라서 소진된 계열 측정값은 30분 동안만 신뢰합니다. 그 뒤에는 측정값을 버리고 해당 계열은 공유 주간 버킷을 대신 사용하며, 그 계열의 다음 요청이 실제 헤더로부터 정확한 상태를 다시 확인합니다. 요청이 거부되면 새 측정값으로 다시 30분 동안 차단이 걸리므로, 실제로 소진된 버킷이라도 그 비용은 계정당 창 하나마다 최대 한 번의 거부된 요청에 그칩니다. 이 창의 길이는 `AIPOOL_FAMILY_STALE_MS`로 조정합니다. 여유가 남은 측정값은 아무것도 차단하지 않으므로 절대 버리지 않습니다.

프로브를 실행하면 이 문제를 완전히 피할 수 있습니다. 프로브는 쿼터를 쓰지 않고 사용량 엔드포인트에서 계열 버킷을 갱신하므로, 리셋이 측정값 신뢰 창 안이 아니라 프로브 간격 한 번 안에 반영됩니다.

프로브는 계열 버킷을 완전히 재검증하며, 여기에는 상한이 없다고 결론 내리는 것도 포함됩니다. 페이로드가 계정의 모델별 주간 상한을 나열하는데 어떤 계열이 그 안에 **없다면**, 캐시된 측정값을 지우고 그 계열은 공유 주간 버킷을 대신 사용합니다. 업스트림이 상한을 없앴는데도 프록시가 계속 그 상한을 기준으로 차단해서는 안 되기 때문입니다. 이런 목록이 없는 페이로드로는 아무것도 증명할 수 없으므로 아무것도 바꾸지 않습니다. 보고된 각 버킷에는 자체 리셋 시각도 함께 실려 오며, 이 값을 그대로 사용합니다. 아직 시작되지 않은 창에는 리셋 시각이 없으며, 이때 막대에는 공유 주간 버킷의 날짜 대신 아무 날짜도 표시되지 않습니다.

## Keep-warm

롤링 방식의 **5시간 세션 창**은 계정이 실제 메시지를 보내야만 시작됩니다. 그래서 사용 중인 계정의 쿼터가 바닥나 로테이션이 한동안 쓰지 않은(cold) 계정으로 넘어가면, 그 계정의 5시간 창은 *그때서야* 시작됩니다. 하필 그 계정의 여유분 전체가 필요한 바로 그 시점에 말입니다. Keep-warm은 유휴 계정의 타이머를 미리 시작해 두므로, 다음 계정이 필요해질 때는 이미 새 창이 일부(또는 전부) 지나 있습니다.

```bash
aipool warmup 600                                      # 600초마다 유휴 계정 워밍업
aipool warmup reset 15:30 --timezone Europe/Moscow     # 매일 15:30 리셋을 목표로 설정
aipool warmup rolling 15:30 --timezone Europe/Moscow   # 15:30에 리셋 기준점을 두고 이후 5시간마다 반복
aipool warmup off                                      # 어느 모드든 끄기
aipool warmup                                          # 현재 설정 표시
```

> ⚠️ **수동적인 쿼터 프로브와 달리, 이 기능은 쿼터를 조금 소모합니다.** 5시간 타이머는 읽기 전용 호출로는 시작할 수 없으므로, keep-warm은 실제(최소한의) 메시지를 보냅니다. 조건에 맞는 유휴 계정마다 이 프록시를 바라보고 해당 계정에 고정된 일회성 `claude -p --bare --model haiku --output-format text "hi"` 프로세스를 실행합니다. 5시간 창이 **아직 시작되지 않은** 계정만 워밍업하고, 비활성화되었거나 스로틀링 중이거나 오류 상태인 계정과 서드파티 백엔드 계정은 건너뛰며, 가장 저렴한 모델을 사용합니다. 그래도 계정마다 창 하나당 약간의 토큰과 5시간/주간 버킷의 일부를 소모합니다. `PATH`에 `claude` CLI가 있어야 합니다. 최소 간격은 60초이며, 변경 사항은 즉시 적용됩니다. 상태는 `aipool status --json`의 `warm` 아래에 표시됩니다.

reset 모드는 목표 벽시계 시각과 IANA 시간대를 설정에 저장한 다음, Anthropic의 고정된 5시간 창을 빼서 각 워밍업 시각을 구합니다. 시작할 때, 설정을 다시 불러올 때, 그리고 매번 실행한 뒤에 다음 달력상 발생 시각을 다시 계산하므로, 일광 절약 시간제가 바뀌어도 일정이 어긋나지 않습니다. 동작 방식은 cron의 의미 체계를 따릅니다. 예약된 시각에 AIPool이 멈춰 있었다면 그 실행은 건너뛰고, 서버는 앞으로 다가올 다음 발생 시각을 기다립니다. CLI의 확인 메시지에는 계산된 현지 시각, UTC 시각, 시간대 오프셋, 다음 발생 시각이 출력됩니다.

rolling 모드는 요청한 현지 시각을 기준으로, 워밍업 시각이 아직 지나지 않은 다음 리셋 시각을 저장한 뒤, 같은 절대 5시간 주기로 워밍업을 무기한 예약합니다. 저장된 기준점(anchor) 덕분에 서비스를 재시작하거나 설정을 다시 불러와도 주기의 위상이 그대로 유지됩니다. 놓친 슬롯은 따라잡기 요청 없이 건너뛰며, AIPool은 원래 주기의 다음 시점을 기다립니다. 어떤 계정의 현재 창이 rolling 슬롯으로부터 2분 이내에 리셋된다고 Anthropic이 보고하면, AIPool은 그 리셋 후 10초가 지날 때까지 기다렸다가 그 계정만 다시 시도합니다. 이때 계정 상태를 먼저 다시 확인하므로, 일반 사용으로 이미 새 창이 시작되었다면 지연된 워밍업은 실행되지 않습니다. 타이머나 토큰 갱신이 그다음 1분을 넘겨 실행되는 경우에도 재시도를 건너뜁니다. 이렇게 계정별로 짧게 지연하는 방식은 전체 주기를 옮기거나 재시작 후 놓친 슬롯을 다시 실행하지 않고도 시계 오차와 리셋 보고의 부정확성을 흡수합니다. 24시간은 5로 나누어떨어지지 않으므로, 요청한 벽시계 시각에 일어나는 리셋은 기준점 리셋뿐입니다. 이후의 리셋 시각은 현지 시계상에서 계속 이동하며, 일광 절약 시간제 변경으로 표시되는 현지 시각이 달라질 수도 있습니다. CLI는 각 rolling 시점을 그 시점의 UTC 오프셋 및 ISO 타임스탬프와 함께 출력하므로, 일광 절약 시간제 때문에 같은 벽시계 시각이 반복되더라도 모호하지 않습니다. 이 기능은 최선의 노력(best effort) 방식으로 동작합니다. 허용 오차를 벗어난 시점에 5시간 창이 진행 중인 계정이나 조건에 맞지 않는 상태의 계정은 해당 슬롯에서 건너뜁니다.

Keep-warm은 프롬프트 캐시와는 관계가 없습니다. [로테이션 간 프롬프트 캐싱](routing.md#로테이션과-프롬프트-캐시)을 참고하세요.

## 전환 임계값

`switchThreshold`는 계정을 로테이션에서 제외하는 기준 사용률입니다. 숫자 하나로 모든 버킷을 제어합니다:

```json
"switchThreshold": 0.98
```

하지만 이 방식은 서로 다른 두 위험을 하나로 뭉뚱그립니다. 두 시간 뒤면 다시 채워지는 5시간 창의 98%는 조금 성가신 정도지만, 6일이 남은 주간 창의 98%는 그 계정을 그 주의 남은 기간 동안 쓸 수 없다는 뜻입니다. 어떤 버킷에서는 다른 버킷보다 더 일찍 다음 계정으로 전환하려면, 숫자 대신 테이블을 지정합니다:

```json
"switchThreshold": { "default": 0.98, "unified7d": 0.9 }
```

키는 쿼터 필드 이름인 `unified5h`, `unified7d`, `unified7dFable`, `unified7dSonnet`, `tokens`, `requests`입니다. 나열하지 않은 버킷에는 `default`가 적용되며, 숫자 하나만 지정하면 이전과 똑같이 동작합니다. TUI의 ±1% 조절 기능은 숫자 하나로 된 형식만 편집합니다. 테이블이 설정되어 있으면 설정 행에 읽기 전용으로 표시되므로, ± 조절 때문에 버킷별 값이 모르는 사이에 하나의 값으로 덮어써지는 일은 없습니다.

두 형식 모두 터미널을 연결하지 않고도 설정할 수 있습니다:

```bash
aipool threshold                  # 실제 적용되는 테이블 표시
aipool threshold 90               # 모든 버킷에 숫자 하나 적용
aipool threshold unified7d=90     # 버킷 하나를 추가하거나 변경
aipool threshold unified7d=default  # 다시 제거
```

실행 중인 서버는 이 명령이 보내는 리로드 요청을 받아 변경 사항을 반영합니다. 버킷별 테이블을 그 자리에서 편집하는 방법은 이것뿐입니다. TUI에서는 테이블이 읽기 전용으로 표시되며, TUI의 숫자 하나 형식으로 편집하면 테이블이 하나의 값으로 덮어써집니다.

### 계정별 임계값

위의 계정 풀 전체 설정은 모든 계정에 숫자 하나(또는 테이블 하나)를 적용하므로, 성격이 다른 계정이 섞인 계정 풀에는 맞지 않습니다. 예를 들어 추가 사용량을 구매한 계정과 그렇지 않은 계정이 함께 있거나, Max 20x 계정과 훨씬 일찍 다음 계정으로 전환해야 하는 Pro 계정이 함께 있는 경우입니다. `accounts[].switchThreshold`는 같은 두 가지 형식으로 이 설정을 계정별로 재정의합니다:

```json
{ "name": "extra-usage@example.com", "switchThreshold": 1.0 }
```

```json
{ "name": "small-plan@example.com", "switchThreshold": 0.9 }
```

값은 전부 아니면 전무 방식이 아니라 버킷 단위로 결정됩니다. 어떤 버킷에 대해 AIPool은 먼저 계정 테이블에서 그 버킷의 항목을 확인하고, 그다음 계정 자체의 `default`(또는 계정별로 지정한 숫자 하나)를 확인하며, 그래도 없을 때만 그 버킷에 대한 계정 풀의 `switchThreshold`를 사용합니다. 따라서 버킷 하나만 지정한 테이블은 그 버킷만 재정의하고, 나머지 버킷은 모두 계정 풀 설정을 이어받습니다:

```json
{ "name": "b@example.com", "switchThreshold": { "unified7dFable": 0.8 } }
```

이 설정은 `b`의 `unified5h`와 `unified7d`를 계정 풀에 설정된 값 그대로 두고, Fable만 80%에서 다음 계정으로 전환합니다.

이 값도 계정 풀 설정과 똑같이 여전히 **선호 기준**입니다. 전체 소진 시의 재검증 프로브가 같은 방식으로 이 값을 무시할 수 있으며, 바로 이 점이 위의 `accounts[].maxUsage` 강제 상한과 다른 설정으로 구분되는 이유입니다. 해당 계정의 막대, `Models` 행, `aipool status`는 그 계정 자체의 값을 기준으로 빨갛게 표시됩니다. 두 값이 모두 설정되었을 때 두 상한이 함께 어떻게 그려지는지는 [계정별 사용량 상한](#계정별-사용량-상한)을 참고하세요.

재정의 값은 계정이 표시되는 모든 곳, 즉 `aipool status`, TUI(라이브 모드와 attach 모드), 웹 대시보드에 나타나지만, 실제로 무언가를 바꾸는 경우에만 표시됩니다. `switchThreshold`가 없는 계정이나, 테이블이 우연히 계정 풀의 값과 똑같은 계정에는 추가 줄이 표시되지 않습니다. `aipool status`에서는 별도의 행으로 표시됩니다:

```
  Weekly   [███████████░░░░░░] 62%
  Fable    [██░░░░░░░░░░░░░░░] 10%
  Models   Opus ✓   Fable ✓
  Switch   switch fable 80%
```

숫자 하나로 재정의한 경우에는 대신 `switch at 100%`로 표시됩니다. TUI와 대시보드는 막대 위의 표시 대신, 해당 계정의 행이나 카드 끝에 붙는 태그/배지로 같은 축약 텍스트를 보여 줍니다. `maxUsage`와 달리 `switchThreshold`는 막대 자체에 백분율로 그려진 적이 없었기 때문에(막대가 빨갛게 바뀌는 지점으로만 쓰였음), 확장할 기존 표시가 없었습니다.

계정의 숫자 하나가 계정 풀의 기본값과 같더라도 버킷 값을 바꿀 수 있습니다. 계정 풀의 버킷별 항목보다 우선순위가 높기 때문입니다. 계정 풀이 `{ "default": 0.98, "unified7d": 0.85 }`일 때 `0.98`로 설정된 계정은 주간 버킷이 85%가 아니라 98%에 이르렀을 때 다음 계정으로 전환되며, `switch 7d 98%`로 표시됩니다.

`maxUsage`와 마찬가지로 이 설정에는 CLI 편집 명령이 없습니다. 설정 파일을 직접 편집한 뒤 실행 중인 서버가 리로드할 때 반영되도록 하거나, 서버를 재시작하세요. 값은 비율이므로 0보다 크고 1 이하인 숫자여야 합니다(`1.0`은 유효하지만 `98`은 유효하지 않습니다). 범위를 벗어나거나 숫자가 아닌 항목은 무시되고, 해당 계정은 그 항목에 대해 계정 풀의 값을 사용하며, 계정과 필드 이름을 담은 로그가 한 줄 남습니다.

## 계정별 사용량 상한

`switchThreshold`는 계정 풀 전체에 적용되며 *선호 기준*입니다. 그 수준에 이르면 로테이션은 다른 계정을 우선하지만, 모든 계정이 임계값을 넘으면 프록시는 그래도 재검증 요청을 하나 보냅니다. 임계값 판단은 오래된 측정값에 근거했을 수 있고, 영원히 거부하는 편이 더 나쁘기 때문입니다. 그래서 "이 계정은 쿼터의 일부만 쓸 수 있다"는 용도에는 맞지 않습니다.

그 용도에 맞는 것이 `accounts[].maxUsage`입니다. 형식은 같고, 계정별로 지정합니다:

```json
{
  "name": "spare@example.com",
  "maxUsage": { "unified5h": 0.6, "unified7d": 0.6, "unified7dFable": 0.8 }
}
```

숫자 하나를 지정하면 모든 버킷에 상한이 걸립니다. 키는 `switchThreshold`와 같은 쿼터 필드 이름이며, 테이블에 없는 버킷에는 `default`가 적용됩니다. 하지만 나열되지도 않고 `default`로도 지정되지 않은 버킷에는 **상한이 없으므로**, 상한은 언제나 직접 지정한 만큼만 걸립니다.

상한에 도달하면 그 계정은 **어떤 요청도 받지 않습니다**:

- 로테이션이 그 계정을 건너뛰며, `aipool status`에 `capped`(또는 `advisor-capped`)로 표시됩니다.
- `switchThreshold`에 따른 판단과 달리, 전체 소진 시의 재검증 프로브도 그 계정을 건너뜁니다.
- 고정된 요청(`TC_ACCT`, `/tc-acct/<name>`)은 상한을 넘어 쿼터를 쓰는 대신 소진 응답을 받습니다. 이 경우에도 고정된 요청이 다른 계정으로 넘어가는 일은 없습니다.

상한은 임계값과 똑같이 모델 단위로 적용됩니다. `unified5h`와 `unified7d`는 모든 모델을 막고, `unified7dFable`은 Fable만 막습니다. 따라서 위 예시에서는 Fable이 상한에 도달한 뒤에도 같은 계정에서 Opus와 Sonnet은 계속 처리합니다. 상한은 지정한 값에 도달하는 순간(`>=`) 적용되며, 리셋된 창은 이전 측정값 때문에 상한에 걸리지 않습니다.

상한은 적용되기 전부터 상태 화면에 표시됩니다. 해당 막대 위에 표시되고, 옆에 백분율로 적히며, `Models` 행에도 반영됩니다:

```
  Session  [██░░░░░░░░░┃░░░░░░] 10% cap 60%
  Weekly   [███████████┃░░░░░░] 62% cap 60%
  Fable    [██░░░░░░░░░░░░┃░░░] 10% cap 80%
  Models   Opus ✗   Fable ✗
  Blocked  account usage cap reached (maxUsage)
```

이 표시는 막대를 넓히지 않고 막대 안에 들어가므로, 상한이 있는 행과 없는 행이 여전히 나란히 정렬됩니다. TUI에서는 막대가 전환 임계값이 아니라 상한에서 빨갛게 바뀝니다.

변경 사항은 설정을 다시 불러올 때 즉시 적용되며, 재시작할 필요가 없습니다.

## 서드파티 백엔드 쿼터

[서드파티 백엔드 계정](accounts.md#서드파티-백엔드-계정)에는 Anthropic 쿼터가 없으므로 막대가 `unknown`으로 표시됩니다. 제공자가 자체 수치를 공개하는 경우에는 프로브가 같은 주기로 그 값을 읽고 상태 화면에 표시합니다:

```
  deepseek (oauth, prio 200) active
  Balance  $25.81
  Probe    ok 2m ago, 210ms
```

읽어 온 값은 `{ label, text, utilization }` 형태로 정규화됩니다. 0~1 사이의 비율을 보고하는 제공자는 다른 버킷처럼 막대로 표시되고, 금액이나 크레딧을 보고하는 제공자는 해당 텍스트가 표시됩니다. 아무것도 공개하지 않는 제공자는 계속 `unknown`으로 표시되며, 없는 값을 지어내지 않습니다.

제공자 지원은 전부 `src/backend-quota.js`에 들어 있으며, 계정의 `upstream` 호스트로 매칭됩니다. 제공자를 추가하려면 그 파일에 항목 하나(경로와 파싱 함수)만 넣으면 됩니다. 프로버, 쿼터 필드, 렌더러는 특정 제공자를 직접 언급하지 않습니다. 현재는 DeepSeek을 지원합니다.

## 소진 시 대기

기본적으로 모든 계정이 소진되면 AIPool은 즉시 `429`를 반환하며, 그러면 Claude Code는 현재 작업을 중단합니다. `holdSeconds`를 설정하면 프록시는 그 대신 **HTTP 연결을 열어 둔 채** 약 60초마다 조용히 확인합니다. 어느 계정이든 쿼터가 리셋되는 순간 요청이 전달되고 Claude Code가 작업을 이어 가므로, 중단이 아예 일어나지 않습니다.

설정 파일(`~/.config/aipool.json`)에서 지정합니다:

```json
"holdSeconds": 3600
```

`aipool run`은 실행하는 Claude Code 프로세스의 `API_TIMEOUT_MS`를 자동으로 `holdSeconds + 60`초로 늘리므로, 클라이언트 측 타임아웃이 대기 창 전체를 포괄합니다. Claude Code를 따로 설정할 필요는 없습니다.

밤새 실행하거나 무인으로 실행할 때 유용합니다. 아침에 일어나 멈춰 버린 작업을 마주하는 대신, 쿼터 창이 열리는 즉시 세션이 조용히 재개됩니다.
